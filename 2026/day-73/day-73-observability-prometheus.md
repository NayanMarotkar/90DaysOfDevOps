# Day 73 — Observability Fundamentals & Prometheus

## Overview

Today I started the Observability section of my DevOps journey by learning the fundamentals of observability and setting up Prometheus for metrics collection.

Traditional monitoring tells us when something is wrong, while observability helps us understand why it is wrong by providing visibility into the internal state of applications and infrastructure.

I explored the three pillars of observability, deployed Prometheus using Docker Compose, learned PromQL basics, and configured Prometheus to scrape metrics from targets.

---

## What is Observability?

Observability is the ability to understand the health and behavior of a system by analyzing the telemetry data it generates.

Unlike traditional monitoring, which focuses on predefined alerts and thresholds, observability enables engineers to investigate unknown issues and identify root causes.

### Monitoring vs Observability

| Monitoring                     | Observability                           |
| ------------------------------ | --------------------------------------- |
| Detects issues                 | Explains issues                         |
| Alert-driven                   | Investigation-driven                    |
| Answers "What happened?"       | Answers "Why did it happen?"            |
| Uses dashboards and thresholds | Uses metrics, logs, and traces together |

---

# The Three Pillars of Observability

## 1. Metrics

Metrics are numerical measurements collected over time.

Examples:

* CPU utilization
* Memory usage
* Request count
* Error rate
* Disk usage

Metrics help answer:

> What is happening in the system right now?

---

## 2. Logs

Logs are timestamped records generated by applications and systems.

Examples:

* Application output
* Error messages
* Authentication events
* Audit logs

Logs help answer:

> Why did something fail?

---

## 3. Traces

Traces follow the journey of a request across multiple services.

Examples:

* API request flow
* Database query latency
* Service-to-service communication

Traces help answer:

> Where did the failure occur?

---

## Why DevOps Engineers Need All Three

Metrics, logs, and traces complement each other.

Example:

* Metrics show a high error rate.
* Logs reveal a database timeout.
* Traces identify the exact service causing the delay.

Together they provide complete visibility into modern distributed systems.

# Prometheus Configuration

## prometheus.yml

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: "prometheus"
    static_configs:
      - targets: ["prometheus:9090"]

  - job_name: "notes-app"
    static_configs:
      - targets: ["notes-app:8000"]
```

---

## docker-compose.yml

```yaml
services:
  prometheus:
    image: prom/prometheus:latest
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'
    restart: unless-stopped

  notes-app:
    image: trainwithshubham/notes-app:latest
    container_name: notes-app
    ports:
      - "8000:8000"
    restart: unless-stopped

volumes:
  prometheus_data:
```

# Prometheus Concepts Learned

## Scrape Targets

Targets are endpoints from which Prometheus pulls metrics periodically.

Example:

```yaml
targets:
  - prometheus:9090
```

Prometheus uses a pull-based model instead of push-based monitoring.

---

## Metric Types

### Counter

A metric that only increases.

Examples:

* Total requests served
* Total errors
* Total logins

Example Metric:

```promql
http_requests_total
```

---

### Gauge

A metric that can increase and decrease.

Examples:

* Memory usage
* CPU utilization
* Active connections

Example Metric:

```promql
process_resident_memory_bytes
```

---

### Histogram

Stores distributions of values in buckets.

Examples:

* Request duration
* Response size

---

### Summary

Similar to Histogram but calculates percentiles client-side.

Examples:

* 95th percentile latency
* 99th percentile response time

---

# Counter vs Gauge

| Counter          | Gauge                     |
| ---------------- | ------------------------- |
| Only increases   | Can increase and decrease |
| Measures totals  | Measures current values   |
| Used with rate() | Used directly             |

### Counter Example

```promql
prometheus_http_requests_total
```

Tracks the total number of HTTP requests served.

---

### Gauge Example

```promql
process_resident_memory_bytes
```

Tracks current memory usage of Prometheus.

---

# PromQL Queries Executed

## 1. Check Target Health

```promql
up
```

Returns:

* 1 = Target is healthy
* 0 = Target is unreachable

---

## 2. Count Total Metrics

```promql
count({__name__=~".+"})
```

Returns the number of metric series currently stored.

---

## 3. Memory Usage

```promql
process_resident_memory_bytes
```

Returns current memory consumption of Prometheus.

---

## 4. Total HTTP Requests

```promql
prometheus_http_requests_total
```

Returns total requests served by Prometheus.

---

## 5. Request Rate

```promql
rate(prometheus_http_requests_total[5m])
```

Returns the per-second request rate over the last 5 minutes.

---

## Bonus Query

Non-200 response rate:

```promql
sum(rate(prometheus_http_requests_total{code!="200"}[5m]))
```

Returns the rate of failed requests over the last 5 minutes.

---

# Data Retention

Prometheus stores metrics in its local Time Series Database (TSDB).

Default retention:

```text
15 days
```

Custom retention example:

```yaml
--storage.tsdb.retention.time=30d
--storage.tsdb.retention.size=1GB
```

When retention limits are exceeded, Prometheus automatically deletes the oldest data blocks.

---

# Importance of Persistent Volumes

```yaml
volumes:
  - prometheus_data:/prometheus
```

Benefits:

* Retains historical metrics
* Survives container restarts
* Prevents data loss
* Enables long-term monitoring

Without a volume mount, all Prometheus data would be lost when the container is recreated.
